§ 02

Request Lifecycle

Every incoming request passes through nine stages in a fixed order. Each stage runs only if the previous one passes.

1
Incoming Request Client
Client sends a POST with an x-api-key header. Two entry points: the direct scan endpoint and the OpenAI-compatible completions proxy which extracts the last user message automatically.
POST /guardrail/scan POST /v1/chat/completions x-api-key: <token> { "text": "…" }
2
API Key Validation Gateway
The gateway checks the key against the Control Plane. A missing or unknown key returns an immediate 401. A valid key resolves to an organization context used for rule lookups and audit logging.
key missing / unknown→HTTP 401
key valid→continue
3
Sanitizer Pipeline Sanitizer
Input runs through a security-ordered transform chain. Each step targets a different attack vector. Data-marking is applied last — so any attacker-injected marker is cleaned away before ours is added. Order is not changeable without breaking security guarantees.
① UTF-8 validate ② NFKC normalize ③ strip default-ignorable ④ strip tag/BIDI/C0-C1 ⑤ strip ANSI escapes ⑥ HTML-strip (bluemonday) ⑦ homoglyph signal ⑧ [DATA]…[/DATA] marking
Output signals passed to ML and gateway:
had_tag_chars had_bidi had_ansi anomaly_score bytes_removed
Anomaly composite: tag chars +0.6 · BIDI +0.3 · ANSI +0.2 · homoglyph +0.3 (capped 1.0)
4
ML Inference ML Service
The sanitized text is sent to the Python FastAPI inference service. Two HuggingFace models run: an injection classifier that returns a label and probability, and a toxicity scorer. Results are merged back into the request context.
injection.score 0–1 injection.label e.g. PROMPT_INJECTION · JAILBREAK · BENIGN toxicity.score 0–1
5
Pre-Policy Hard Blocks Gateway
Before any policy or routing evaluation, the gateway enforces two hard thresholds hard-coded in the request handler. They are a safety floor: no policy rule can override them, not even an allow — they run first and terminate immediately.
anomaly_score ≥ 0.6→HTTP 400 content_filter
injection.score ≥ 0.85→HTTP 400 content_filter
both below threshold→continue to policy engine
6
CEL Policy Engine Policy
Structured policy rules (configured in the Rules page) are evaluated using the Common Expression Language. Each rule has typed conditions on ML signal fields combined with AND/OR logic, plus an action. Rules evaluate in order — the first matching allow or block rule wins and evaluation stops; a matching log rule is recorded and evaluation continues with the next rule. The Rules page UI provides a query-builder interface to author these conditions without writing CEL by hand.
policies cannot be loaded, compiled or evaluated→HTTP 503, nothing sent upstream
injection.score injection.label anomaly.score anomaly.has_tag_chars anomaly.has_bidi request.model request.tokens
7
Route Engine Routing
The visual flow diagram defined in the Routing page is loaded and evaluated. Each condition node is a raw CEL expression string. The engine walks the directed graph from the START node, evaluates conditions, and follows matching edges to an Action node. If no condition matches, a default action applies.
condition node evaluates true→follow edge to action node
no rule matches→default action
8
Action Execution Gateway
The resolved action is executed and every outcome gets one audit row. ALLOW forwards the sanitized request to the upstream LLM; a request that only matched LOG rules is allowed. REDACT and ROUTE are not implemented: the control plane refuses them, and a stored rule that matches with one fails closed. If the client hangs up while the upstream is still working, the upstream request is cancelled at once. The answer then passes the output guard before it reaches the client: markdown and HTML images, links to hosts not on the allowlist and image URLs carrying a query are removed; email, Vietnamese phone, CCCD and card numbers (and optionally IPv4) become [REDACTED:type]; a per-request canary token placed in the system prompt is blocked or redacted if the model repeats it. Whole responses are rewritten in choices[].message.content; streams keep a 256-character window per choice so a pattern split across chunks is still caught.
BLOCK → HTTP 400 content_filter ALLOW → forward to upstream LOG → audit, next rule decides REDACT → not implemented, HTTP 503 ROUTE → not implemented, HTTP 503 output: images, links, PII, canary
9
Audit Log Storage
Every request and its full signal set is persisted to PostgreSQL regardless of outcome. action is allow, block, error (the upstream failed) or output_leak (the canary appeared in the answer). What the output guard removed is counted per type in pii_entities as output:<type>=<n>, never with the content. Rows still in flight at shutdown are waited for. The Control Plane API exposes this data to the Dashboard's live request feed (polled every 5 s).
action pii_entities (output counts) injection_score injection_label toxicity_score anomaly_score had_tag_chars had_bidi latency_ms created_at
§ 03

Two Types of Rules

Policy rules and routing rules are entirely separate systems — different UI pages, storage schemas, evaluation engines, and operational status. They share the word "rule" but nothing else.

Policy Rules

Rules page · /rules · Step 6 in lifecycle
Purpose
Decide whether to block, allow, or log based on structured conditions on ML signal values
Condition type
Query-builder: pick a field, an operator (>=, ==, contains, …) and a value; combine clauses with AND / OR
Fields available
injection.score, anomaly.score, injection.label, anomaly.has_bidi, anomaly.has_tag_chars, request.model, request.tokens, request.tenant_id, mcp.is_tool_response. toxicity.score, pii.entities and topic.categories were removed: no detector produced them. New rules naming them are refused; stored ones still evaluate them as zero or empty.
Evaluation
CEL engine, evaluated in the order rules are listed; the first matching allow or block wins, log rules record a match and let evaluation go on
Storage
JSON in PostgreSQL via Control Plane API
Status
● Live
Example — block moderate-injection requests
{
  "name": "block-high-injection",
  "condition": {
    "combinator": "and",
    "rules": [
      {
        "field": "injection.score",
        "operator": ">=",
        "value": 0.7
      }
    ]
  },
  "action": "block"
}

Route Rules

Routing page · /routing · Step 7 in lifecycle
Purpose
Visual flow diagram that decides where to route a request — block it, allow it, or send it to a specific upstream model
Condition type
Raw CEL expression string written directly into a condition node; the full CEL language is available
Node types
START → one or more CONDITION nodes → ACTION node; nodes connected with directed edges in the drag-and-drop editor
Evaluation
Graph walk from START; evaluate each condition node's CEL string; follow the matching edge; reach an ACTION node
Storage
React Flow diagram JSON exported and stored in Control Plane
Status
● Live
Example — CEL condition node expression
// Condition node:
injection_score >= 0.6 &&
  injection_label == "PROMPT_INJECTION"

// True → connected ACTION node:
{
  "action": "block",
  "reason": "injection detected"
}

// False → next condition node or default
